## Logs Everywhere
A network is basically a bunch of devices constantly talking to each other and out to the internet through a router, endpoints servers websites all of it. Every single one of these is generating logs nonstop as things happen, and these devices are basically what get called log sources. These logs are the trail of everything happening across the network and theyre genuinely critical for spotting malicious activity or just general troubleshooting. Log sources generally split into two categories

Host centric logs are events that happened within or tied directly to a specific host, think windows and linux machines servers etc. Examples of stuff that falls here

- a user accessing a file
- a user attempting to authenticate
- a process actually executing
- a process modifying a registry key or value
- powershell execution

Network centric logs come from communication between hosts or out to the internet, generated by stuff like firewalls ids/ips and routers. Examples here

- ssh connections
- a file accessed over ftp
- general web traffic
- a user connecting through vpn
- network file sharing activity

Together these two categories are just constantly pumping out logs across a network nonstop

## The Problem With Isolated Logs
Having all these logs sounds great in theory but working with them raw comes with real challenges

- too many sources — a network has a ton of log sources generating hundreds of events a second, scattered across totally different devices, manually checking each one during an incident is painfully tedious
- no centralization — since logs just sit on whatever device generated them, investigating means connecting into each one individually through ssh rdp or whatever, which wastes a ton of time during an actual investigation
- limited context — a single log in isolation often looks completely harmless. Like a file access event on its own is normal, but correlated against other logs it might reveal that access came from a user who got onto that machine through lateral movement after compromising something else first
- limited analysis — with the sheer volume of logs being generated per second, manually reviewing all of it for abnormal activity just isnt realistic, analysts will inevitably miss stuff buried in the noise
- format issues — different log sources output in completely different formats, so an analyst would need to understand every single ones format just to read them properly, which gets brutal fast once youre dealing with a lot of different device types

## What SIEM Actually Solves
Siem or security information and event management is the tool built specifically to fix all of the above. It pulls logs in from all kinds of sources, standardizes their format into something consistent, correlates them together, and runs detection rules against all of it to actually catch malicious activity

## Core SIEM Features
Centralized log collection is the first big win, siem pulls logs from everywhere endpoints servers firewalls etc through lightweight agents or apis and dumps it all into one central place, killing the need to jump machine to machine manually

Normalization solves the format problem. Parsing is breaking a raw log down into individual fields so its actually readable, and normalization is taking logs from totally different sources and converting them all into one consistent format so a windows log and a linux log end up looking structurally similar inside the siem

Correlation is where the real value shows up. Individual logs on their own arent that useful, but siem links logs from different sources together to spot patterns. Like say within a 5 minute window someone logs in via vpn from an ip they never used before, then accesses some shared drive documents, then runs a powershell script, then the system makes an outbound connection. None of these look alarming individually, but correlated together it starts looking a lot like a compromised account doing data exfiltration

Real time alerting comes from detection rules built into the siem, some come default out of the box and analysts also write custom ones based on their own environment. When a rules conditions get met an alert fires and the analyst gets notified to go investigate

Dashboards and reporting tie it all together visually, presenting normalized data as actionable summaries. Common stuff youd find on a dashboard includes alert highlights system notifications health alerts failed login lists total events ingested rules that have triggered and top domains visited. Every siem ships with some default dashboards and also lets you build custom ones on top

Theres more to siem beyond this too, like threat intel feed integration long term data retention and strong search capability, just not covered in depth here

## Log Sources in Practice
Windows machines log everything through event viewer, each event type gets a unique id which makes searching and tracking way easier. These logs from every windows endpoint typically get forwarded straight to the siem for centralized monitoring

Linux keeps logs scattered across a few common locations

- /var/log/httpd — http request response and error logs
- /var/log/cron — anything related to cron job execution
- /var/log/auth.log or /var/log/secure — authentication related logs
- /var/log/kern — kernel level events

A cron log entry generally looks something like a timestamp hostname process name and whatever the cron daemon reported, like a job running or failing to execute

Web servers need to be watched closely too since all incoming and outgoing requests can reveal attack attempts. On linux apache logs usually live around /var/log/apache or /var/log/httpd, and a typical entry shows the requesting ip timestamp the actual request method and path the response status code and the user agent string

## How Logs Actually Get Into a SIEM
Theres a few common ingestion methods siem platforms use

Agent or forwarder is a lightweight tool installed directly on an endpoint that captures relevant logs and ships them off to the siem server, splunk calls this a forwarder specifically

Syslog is a widely used protocol for pulling data from stuff like web servers and databases and sending it in real time to a centralized destination

Manual upload lets you dump offline log data straight into the siem for quick one off analysis, gets normalized and made searchable same as anything else once ingested

Port forwarding has the siem sitting and listening on a specific port while endpoints are configured to forward their data straight to that listening port

## How Detection Rules Actually Work
Detection rules are really just logical expressions set up to trigger when specific conditions get met. A few example rule ideas

- five failed logins within 10 seconds — alert for multiple failed login attempts
- a successful login right after several failed attempts — alert for successful login after failed attempts
- any usb plugged in — useful specifically if usb use is against policy
- outbound traffic over some threshold like 25mb — potential data exfiltration alert, threshold usually set based on whatever the company considers normal

Building an actual rule usually comes down to picking the right log source event id and any relevant fields. Like adversaries clearing logs post exploitation to cover their tracks trigger event id 104 in windows, so a rule watching for log source WinEventLog and EventID 104 would catch that specifically as an event log cleared alert

Another example, something like whoami commonly gets run right after gaining access or escalating privileges. Building a rule for this means figuring out the right log source, the event id tied to process execution which is 4688 in windows, and watching the NewProcessName field specifically for whoami showing up. A rule like log source WinEventLog and EventCode 4688 and NewProcessName contains whoami would catch that pattern and fire a whoami command detected alert

This is exactly why normalized logs with consistent field value pairs matter so much, detection rules are literally just watching for specific field values to match, and that only works cleanly if the underlying logs are actually structured consistently

## Alert Investigation
Analysts spend a lot of their actual time living in dashboards since they summarize network activity in a digestible way. Once an alert fires, the associated events or flows get pulled up and checked against exactly which rule conditions were met, and from there the analyst decides if its a true or false positive

Depending on what the investigation turns up a few different actions follow

- false positive — the rule might need tuning so it doesnt keep firing on the same harmless pattern
- true positive — move into deeper investigation
- reach out to the asset owner to ask about the activity directly if context is unclear
- confirmed suspicious activity — isolate the affected host
- block the suspicious ip if one is involved
